# 更改清单 v2

**状态**：Draft  
**用途**：作为基于新 boundary 的治理改造执行方案  
**边界依据**：`docs/governance/openspec-harness-boundary.md`（当前状态为 Proposed）  

---

## 1. v2 的核心结论

v1 的方向有一半是对的：确实需要清理重复定义、收薄 `.claude/commands/` / `.claude/agents/`、补 `harness/governance/` 的承载位置。

但 v1 的主要问题是把大量 **执行治理** 和 **研究写作指导** 也一起搬进了 OpenSpec，导致改造过猛，且不完全符合新 boundary。

**v2 的总原则**：

1. **先治理评审，再执行迁移**  
   这类改造先走 `governance-review-workflow.md`，不直接按清单落地。

2. **优先“拆分”而不是“整文件搬家”**  
   如果一个文件同时包含 canonical policy 和 execution guidance，优先拆成两份，而不是整份移动。

3. **优先补齐现有真源，不优先新增大量新 spec**  
   能并入已有 `openspec/specs/**` 的，不新开 spec；避免把重复定义从 Harness 搬成 OpenSpec 内部重复定义。

4. **Harness 继续承载 execution workflow / derived checks / orchestration / research writing guidance**  
   不是所有带 “policy / rules” 命名的文件都应进入 OpenSpec。

5. **Skill / command / agent 入口一律变薄**  
   只保留动作私有逻辑；repo 级治理、边界、路由规则改为引用 Harness / OpenSpec。

---

## 2. 这次改造的目标

本次改造的目标不是“把所有看起来像 policy 的文件都移到 OpenSpec”，而是：

- 明确 OpenSpec / Harness / Skill-command 的单一事实源
- 清掉最明显的职责越界和重复定义
- 给 agent 边界、升级路由、失败降级策略找到稳定承载位置
- 把高风险的大迁移拆成多个可停顿、可回滚、可评审的小阶段

---

## 3. v2 的边界判断

### 3.1 OpenSpec 应承载

- artifact contract
- canonical structure
- asset placement / apply admission
- evidence 等级与正式证据约束
- research object model
- 长期产物质量硬约束
- 即使没有 agent 也仍成立的正式规则

### 3.2 Harness 应承载

- execution workflow
- derived checks
- execution-facing governance
- multi-agent orchestration
- source collection / validation 配方
- traceability 操作流程
- terminology lifecycle
- update / review / repair 操作约定
- research writing guidance
- diagram execution guidance 与 review checklist

### 3.3 Skill / command / agent 应承载

- 动作入口
- 读取哪些正式输入
- 调用哪些工具 / MCP / skill
- 本动作的局部 fallback
- 指向 OpenSpec / Harness 真源的引用

---

## 4. 对 v1 的修正结论

### 4.1 明确保留的判断

以下方向继续保留：

- 新建 `harness/governance/`
- 把 `.claude/agents/CONTRACT.md` 中 repo 级 agent 分类与边界抽到 `harness/governance/agent-boundaries.md`
- `.claude/commands/**` 删除 repo 级治理内嵌，改为引用 boundary / workflow / governance 文档
- `docs/governance/knowledge-directory-model-redesign.md` 视情况改为 archived rationale
- `harness/rules/general/repo-governance.md` 收薄为引用页

### 4.2 明确否决的判断

以下动作 **不再按 v1 执行**：

- 不做 `traceability-policy / terminology-policy / update-policy` 的整文件迁移到 OpenSpec
- 不做 `source-validation-rules.md` 的整文件迁移到 OpenSpec
- 不做 `research/atom-* / note-comparison / component-quality / consensus-depth` 的整文件迁移到 OpenSpec
- 不做 `writing/` 目录的整目录迁移和删除
- 不做 `diagram-policy.md` 的整文件迁移
- 不一次性新增 `writing-policy / research-writing-policy / source-validation-policy` 等多份新 spec
- 不为“目录看起来纯”而先创建空的 `harness/checklists/`

### 4.3 明确改成“候选拆分”的判断

以下文件可能需要未来拆分，但 **不在本轮直接整份搬家**：

- `harness/rules/diagrams/diagram-policy.md`
- `harness/rules/writing/*.md`
- `harness/rules/general/traceability-policy.md`
- `harness/rules/general/update-policy.md`

这些文件的处理方式是：

- 先识别其中哪些是正式 contract
- 再识别哪些是 execution procedure / checklist / skill binding
- 只有在拆分边界清楚后，才新增对应 OpenSpec spec 或 Harness playbook

## 7. 分阶段执行方案

## Phase 0：Governance Review Gate

**目标**：先确认本次改造的边界与范围，而不是直接动目录。

**必须完成**：

- 建立本次治理改造的 review 输出
- 用 `docs/governance/openspec-harness-boundary.md` 检查职责归属
- 用 `openspec/config.yaml`、`schema.yaml`、`workflow/_index`、`rules/_phase_index` 检查影响面
- 形成明确结论：哪些内容是“保留”、哪些是“拆分”、哪些是“延后”

**Gate**：

- `approved`
- 或 `approved with minor fixes`

未过 gate 前，不做大规模路径迁移或删除目录。

---

## Phase 1：低风险收口

**目标**：先修正最明显的职责越界，不动主规则布局。

**执行项**：

1. 新建 `harness/governance/agent-boundaries.md`
2. 从 `.claude/agents/CONTRACT.md` 移出“Agent 分类”与 repo 级协作边界
3. 让 `.claude/agents/CONTRACT.md` 只保留 agent 合同格式、主会话边界、写入范围、禁止事项等通用合同
4. 清理 `.claude/commands/**` 中 repo 级治理内嵌，改为引用 boundary / workflow / governance
5. 将 `harness/rules/general/repo-governance.md` 改成薄引用页
6. 评估 `docs/governance/knowledge-directory-model-redesign.md` 是否可标注为 archived rationale

**这一阶段不做**：

- 不移动 `harness/rules/**` 到 `openspec/specs/**`
- 不更新 `_phase_index.yaml` 的规则路径
- 不删除 `harness/rules/writing/`

---

## Phase 2：去重而非迁移

**目标**：把重复的正式约束收拢到现有 OpenSpec 真源，但尽量不引入新 spec。

**执行策略**：

1. 先做重复约束审计，识别以下几类重复：
   - evidence 状态与验证约束
   - 长期 artifact 质量硬约束
   - research object / dependency / depth 约束
   - apply / asset placement 约束

2. 优先并入现有真源：
   - 正文级硬约束 → `openspec/specs/analysis-principles/spec.md`
   - 长期产物质量与结构 → `openspec/specs/canonical-output-model/spec.md`
   - evidence 等级与验证状态 → `openspec/specs/evidence-policy/spec.md`
   - 对象模型、依赖、深度 → `openspec/specs/research-object-model/spec.md`

3. 收缩 `openspec/config.yaml` 与 `schema.yaml` 中重复但偏执行的 instruction 表述

4. 保持 Harness 侧文件仍可工作；如果只是 OpenSpec 真源补齐，不强制改 Harness 路径

**Gate**：

- 新增 spec 必须证明“现有 spec 无法合理承载”
- 若只是为了目录对称而新增 spec，则拒绝

---

## Phase 3：选择性拆分 mixed files

**目标**：只拆真正混合了 formal rule 与 execution guide 的文件。

**优先候选**：

1. `harness/rules/diagrams/diagram-policy.md`
2. `harness/rules/writing/*.md`
3. `harness/rules/general/traceability-policy.md`
4. `harness/rules/general/update-policy.md`

**拆分规则**：

- Formal contract 进入 OpenSpec 的前提：
  - 没有 agent 也仍成立
  - 属于 repo 级正式约束
  - 不依赖具体 skill / tool / script / fallback

- Execution 部分留在 Harness：
  - 检查步骤
  - review / repair / validation 机制
  - skill / script / command / MCP 绑定
  - handoff / checklist / fallback / escalation

**示例**：

- `diagram-policy.md` 中“研究类型需要什么图、长期 artifact 的交付约束”可候选进入 OpenSpec  
- `diagram-policy.md` 中“必须通过哪个 skill、如何校验、失败如何回修”继续留在 Harness

---

## Phase 4：路径切换与引用更新

只有在 Phase 3 真实发生“文件拆分并落位”之后，才进入这一步。

**更新对象**：

- `AGENTS.md`
- `harness/rules/_index.yaml`
- `harness/rules/_phase_index.yaml`
- `harness/workflows/**`
- `.claude/commands/**`
- `.claude/agents/**`
- `skills/**`

**原则**：

- 只更新已经真实变化的路径
- 不做“预先改路径”
- 不在路径尚未稳定前批量改引用

---

## 8. 不在 v2 范围内的动作

以下内容不纳入本轮：

- 一次性移动 20+ 个 `harness/rules/**` 文件到 `openspec/specs/**`
- 为了目录整洁而删除 `harness/rules/writing/`
- 因为目录样式建议而创建空的 `harness/checklists/`
- 在 boundary 仍为 Proposed 时直接把目标结构视为最终真相
- 重写 `openspec/config.yaml` / `schema.yaml` 的基本 artifact contract

## 10. 验收标准

完成 v2 后，至少满足：

- OpenSpec 与 Harness 的边界判断可被 `governance-review-workflow.md` 复核
- `.claude/commands/**` 与 `.claude/agents/**` 不再内嵌 repo 级治理主定义
- `harness/governance/` 至少承载 agent 协作边界真源
- 不新增明显重复的 OpenSpec spec
- `harness/rules/_index.yaml` 与 `_phase_index.yaml` 没有悬空引用
- 任一阶段中止后，仓库仍保持可用，不依赖“全部迁完才工作”

## 11. 一句话执行建议

**先做“治理收口”和“引用收薄”，再做“formal contract 抽取”；不要把这次改造做成一次性大搬家。**
