# 知识更新政策

## 目的

定义如何安全地更新现有长期资产，同时保持可追溯性与兼容性。

## 何时需要更新

### 必须更新

1. 规范或标准有实质变化
2. 发现事实错误或证据等级不匹配
3. 生态演进导致原结论失效或边界变化

### 通常不需要单独更新

1. 纯格式调整
2. 不影响语义的措辞优化
3. 明显拼写修复

## 标准流程

```text
1. 创建 OpenSpec change
2. 读取现有长期资产
3. 评估影响范围
4. 在 change packet 中完成 request / plan / draft
5. 通过 review
6. 由 publish / apply 阶段提炼回长期资产
```

## 更新类型

| 类型 | 说明 | 典型场景 |
|------|------|----------|
| `minor-update` | 补充细节或修正错误 | 修正机制表述、补证据 |
| `major-update` | 结论或边界发生实质变化 | 规范升级、核心机制变化 |
| `refactor` | 重组结构但不必然改变主结论 | 结构重写、合并章节 |

## 兼容性要求

### 术语兼容

- 不应在未说明的情况下重命名核心术语
- 如术语边界改变，必须在本轮 change 中写清影响

### 结构兼容

- 不应把旧长期资产直接删除而不解释替代关系
- 如重组目录或章节，应在 change packet 中记录迁移说明

### 结论兼容

| 变化类型 | 处理方式 |
|----------|----------|
| 修正错误 | 明确指出旧结论为何失效 |
| 补充细节 | 可增量更新原 artifact |
| 改变结论 | 必须在 draft / review 中明确旧结论失效条件 |

### 增量更新约束（禁止全量替换）

- **禁止全量替换旧 artifact**：新 draft 必须以旧 artifact 为基础进行扩充和优化，不得删除旧内容后只写新内容。
- **保留既有内容**：旧 artifact 中仍然有效的章节必须保留，可以重写表述、补充细节、调整结构，但不能以"不相关"或"非重点"为由直接删除。
- **增量优先**：优先采用增量插入、段落扩充、子章节新增等方式；仅在旧章节整体失效（结论被推翻）时才允许整章替换。
- **替换需说明**：如果确实需要删除旧章节，必须在 draft 中明确说明删除理由和替代内容的位置。
- **全量替换判定**：publish-agent 在 update impact scan 中必须检查新旧 artifact 的行数和章节覆盖率，如旧内容丢失率 > 50%，必须标记为 `needs-justification` 并回报主会话。

## 影响范围评估

更新现有知识时，至少检查：

1. 当前长期资产自身是否需要整体重写
2. 是否有上层 synthesis / decision 直接依赖该对象
3. 是否需要 follow-up change 而不是在本轮全部吞下

### 依赖检查方式

优先检查：

- 相关 `plan.md` 中的依赖声明
- 相关 `artifact.md` / `verdict.md` 中的明确引用
- 当前仓库内的 comparison / decision 产物

不再把 `dependencies.md` 作为主线依赖来源。

## 记录方式

本仓库默认以以下位置记录更新理由与影响：

- `openspec/changes/<change-id>/request.md`
- `openspec/changes/<change-id>/plan.md`
- `openspec/changes/<change-id>/draft.md`
- `openspec/changes/<change-id>/review/`
- git history

如某长期目录已经维护本地 changelog，可同步更新；否则不强制新增 `changelog.md`。

## 停止并人工判断的场景

- 新来源与旧结论发生系统性冲突
- 更新范围扩散到多个上层研究
- 兼容性处理无法在本轮 change 中说清
