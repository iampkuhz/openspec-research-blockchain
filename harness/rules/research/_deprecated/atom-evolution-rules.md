# 演进分析写作规则

## 目的

规范 synthesis/evolution 类型分析的写作结构和内容要求。

## Evolution Atom 结构

```markdown
# 演进概述

[演进的时间范围、关键里程碑]

## 演进阶段

### 阶段 1: [名称]

- 时间范围
- 关键事件
- 主要变化
- 驱动因素

### 阶段 2: [名称]

...

## 演进驱动因素

### 技术驱动

- ...

### 生态驱动

- ...

### 问题驱动

- ...

## 不变的原则

[演进过程中保持不变的核心设计原则]

## 关键分歧点

[曾经讨论但最终未采用的方向]

## 当前状态

[最新状态，待决问题]
```

## 写作要求

### 必须按时间线组织

**禁止**跳跃式叙述。

**必须**：
- 明确时间范围
- 标注关键日期
- 按因果顺序组织

### 阶段叙事主线

每个阶段必须回答三个问题：
1. **新增了什么**：能力、组件、集成
2. **抛弃了什么**：被替代的旧架构、被移除的旧模式
3. **代表了什么技术思考**：为什么这样做，解决什么问题，反映了什么设计哲学

**禁止**仅罗列版本号和日期。版本号和发布日期仅作为辅助标注，不得作为主结构。

### 必须区分变化类型

| 类型 | 描述 | 示例 |
|------|------|------|
| Breaking | 破坏兼容性 | EIP 版本升级 |
| Additive | 新增功能 | 新增 opcode |
| Clarification | 澄清说明 | 补充文档 |
| Optimization | 优化 | Gas 优化 |

### 必须说明驱动因素

**禁止**只描述"发生了什么"。

**必须**解释：
- 为什么发生这个变化
- 什么问题驱动
- 谁推动的

### 总-分结构

每个阶段章节必须以一段总述开头，概括该阶段的核心特征与技术思考，然后再展开具体条目。

### 列表维度一致性

同一层级的列表条目必须处于同一维度。禁止混用：
- "新增某文件"（物理变更）与"某种设计模式"（抽象概念）
- "版本号"（元数据）与"架构变化"（实质变更）
- "新增"与"抛弃"不得混排在同一列表中

### 禁止无意义精确数字

**禁止**罗列对项目理解无意义的精确数字，如：
- "initial commit 有 39 个文件"
- "约 200 行代码"
- "544+ commits"
- "24 个 release"

仅在数字本身代表关键架构决策时才使用精确数字（如"移除了约 200 行自定义工具调度代码，迁移到框架原生方案"）。

### 阶段划分原则

**阶段必须按"架构模式变化"划分**，而非按版本号或时间窗口机械切分。
- 每个阶段应代表一次架构跃迁（如"从 X 模式变为 Y 模式"）
- 同一阶段内的变化应属于同一主题
- 如果某段时间只有 bug 修复和版本迭代，不应单独拆成阶段，应归入"成熟维护期"或合并到上一个阶段
- 阶段命名应反映架构特征（如"OpenAI 直连工具"、"SaaS Pro 平台化"），而非版本号范围

### 总-分结构示例

每个阶段章节的开头必须有一段总述，示例格式：

> **阶段 X：[名称]**（时间范围）
>
> 该阶段的核心技术思考是 [一句话概括]。项目从 [旧模式] 转向 [新模式]，主要解决 [什么问题]。具体体现在以下 N 个方面：
>
> - [维度 1 的变化]
> - [维度 2 的变化]

### 列表维度示例

**错误示例**（混用维度）：
```
- 新增 repo_tools.py          ← 物理变更
- 工具拦截器模式              ← 设计模式
- v0.2.0 是第一个有版本号的 release  ← 元数据
```

**正确示例**（同一维度 — 能力层面）：
```
- 能力层：RLM 工具集从"分析 diff"扩展到"探索仓库"，新增文件读取、目录列出、代码搜索三种工具
- 架构层：引入工具拦截器模式，RLM 生成的工具调用被拦截并转为 GitHub API 请求
- 生态层：添加 asyncreview skill，支持被其他 agent（Claude、Cursor 等）作为 Skill 调用
```

### 图表要求

演进类 artifact 必须包含至少一张演进路线图。图表不仅用于展示架构图，演进图也应通过图表展示以减少阅读疲劳。

演进路线图示例（ASCII）：
```
一次性 diff 分析 → Agentic 仓库探索 → 多轮递归推理 → 原生工具迁移简化 → 本地模式
   (起点)            (能力扩展)         (状态引入)      (架构简化)       (场景扩展)
```

如有多个正交演进维度（如 agent 生态扩展、协议标准化、平台扩展），应分别用独立图表展示，而非挤在一张图中。

## 质量检查清单

- [ ] 时间线是否清晰
- [ ] 是否区分变化类型
- [ ] 是否说明驱动因素
- [ ] 是否列出关键分歧点
- [ ] 是否说明不变原则
- [ ] 当前状态是否更新
- [ ] 每个阶段是否回答了"新增什么、抛弃什么、代表什么技术思考"
- [ ] 是否包含演进路线图（ASCII 或 PlantUML）
- [ ] 每个阶段章节是否有总述段落
- [ ] 列表条目是否处于同一维度
- [ ] 是否避免了无意义的精确数字
