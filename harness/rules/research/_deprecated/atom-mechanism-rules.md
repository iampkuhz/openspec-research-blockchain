# 机制分析写作规则

## 目的

规范 `mechanism atom` 的写作结构、必要图表和抽象边界，确保：
- 先区分角色、组件、状态，再进入正文
- 机制分析覆盖边界、内部实现、跨角色流程和状态转换
- 不把角色、组件、状态混在一张图里

## 核心定义

| 类型 | 判断标准 | 典型问题 | 常见表达 |
|------|----------|----------|----------|
| **Role（角色）** | 控制方不同，跨边界通信依赖 trust assumption | 谁和谁交互？ | 角色边界图、时序图 |
| **Component（组件）** | 控制方相同，属于同一操控者内部实现 | 该角色内部如何分层？ | 内部组件图 |
| **State（状态）** | 同一角色/组件的运行阶段 | 什么时候转移？为什么转移？ | 状态图、状态表 |
| **Data Object（数据对象）** | 消息、证书、区块、证明等 | 传递了什么？ | 图中的 note / 消息标签 |

**重要**：
- `Proposer` / `Leader` / `Aggregator` 这类临时职责，若只是某角色在特定阶段承担的功能，默认不是独立组件。
- `Round` / `Phase` / `ChallengeWindow` / `Locked` 这类概念，默认不是组件，应落入状态视图。

## Mechanism Atom 最小结构

```markdown
# 概述

## 实体分类表

| 实体 | 类型 | 控制方 | 是否跨信任边界 | 主要职责 | 应落入哪类图 |
|------|------|--------|----------------|----------|--------------|

## 图表清单表

| 图名 | 解决的问题 | 是否必须 | 格式 | 备注 |
|------|------------|----------|------|------|

## 角色与信任边界（按条件必需）

## 角色内部组件（按条件必需）

## 核心流程

## 状态转换（按条件必需）

## 关键设计决策

## 边界情况 / 失败条件

## 复杂度 / 成本（如适用）
```

## 必要图表规则

### 1. 实体分类表（必须）

在画任何图之前，必须先把正文中的关键实体分类为：
- role
- component
- data object
- state
- external system

**禁止**跳过这一步直接作图。

### 2. 图表清单表（必须）

在正文中必须显式写出：
- 计划交付哪些图
- 每张图回答什么问题
- 哪些图是必需，哪些被省略
- 省略的理由是什么

### 3. 角色与信任边界图（按条件必须）

满足任一条件时，必须提供：
- 存在两个及以上独立控制方
- 需要解释 trust assumption
- 需要解释谁向谁发送消息、证明或调用

### 4. 角色内部组件图（按条件必须）

当机制需要解释单个核心角色内部的模块分工时，必须提供。

**复用规则**：
- 如果多个角色内部结构相同，只画 1 张 canonical 图
- 用 Markdown 表格补充各角色差异

### 5. 跨角色核心流程图（按条件必须）

当机制依赖跨角色交互时，必须提供至少 1 张 happy path。

若以下内容影响安全性、活性、资金安全或可恢复性，还必须补充异常路径图或表：
- timeout
- challenge
- rollback
- retry
- slash / dispute
- fallback path

### 6. 状态转换图/表（按条件必须）

当行为依赖以下任一要素时，必须提供状态图或状态表：
- 命名状态
- phase / stage
- round / epoch
- timeout
- challenge window
- lock / unlock

## 文字写作要求

### 必须解释为什么

**禁止**只描述"是什么"。

**必须**解释：
- 为什么这样设计
- 替代方案是什么
- 为什么排除替代方案

### 必须写清边界

**必须**：
- 明确机制的适用范围
- 说明不适用场景
- 列出关键假设条件
- 说明哪些结论依赖状态机或信任边界

### 图文分工

- 图承担主干结构
- 文字只补充图中不易表达的设计原因、trade-off、边界情况
- 禁止用大段文字完整复述图里已经清楚表达的步骤

## 常见错误

### 错误 1：把角色当组件

**错误示例**：
- 把 `Proposer`、`Validator`、`User` 与 `Consensus Engine` 并列画在一张组件图中

**修复方式**：
- 角色进入边界图/时序图
- 组件保留在单角色内部组件图

### 错误 2：把状态当组件

**错误示例**：
- 把 `Prevote`、`Commit`、`Challenge Window` 画成组件框

**修复方式**：
- 改为状态图或状态转换表

### 错误 3：没有先做覆盖规划

**错误示例**：
- 直接写正文，最后补一张"万能大图"

**修复方式**：
- 先写实体分类表
- 再写图表清单表
- 最后按视图逐个交付

## 质量检查清单

- [ ] 是否有实体分类表
- [ ] 是否有图表清单表
- [ ] 是否解释设计动机
- [ ] 是否列出替代方案
- [ ] 是否有边界说明
- [ ] 是否覆盖边界情况
- [ ] 是否有复杂度/成本分析（如适用）
- [ ] 是否把角色、组件、状态区分正确
- [ ] 多角色机制是否有角色与信任边界图
- [ ] 跨角色机制是否有核心流程图
- [ ] 有显式状态转换时是否有状态图或状态表
