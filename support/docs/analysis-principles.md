# 分析原则

> 角色：说明版。仓库级硬规范见 [openspec/specs/analysis-principles/spec.md](/Users/zhehan/Documents/tools/llm/openspec/openspec-research-blockchain/openspec/specs/analysis-principles/spec.md)。

## 总原则

本仓库的分析顺序固定为：

1. 先机制
2. 后价值
3. 先事实
4. 后判断
5. 先边界
6. 后结论

## 机制优先

面对任何协议、EIP、网络、机制，优先回答：

- 对象是什么
- 它处理哪个问题
- 它的最小工作流是什么
- 状态在哪些参与方之间流动
- 为什么这样设计
- 不这样设计会怎样

如果机制层没讲清楚，就不要提前下价值结论。

## 设计原因优先

不要只写“它做了什么”，而要写：

- 它为什么要这么做
- 它替代了什么
- 它规避了什么问题
- 它引入了什么代价

研究的重点是设计原因，不是表面功能。

## 边界优先

任何结论都必须说明边界：

- 它适用于哪些前提
- 它不覆盖哪些问题
- 它依赖哪些角色或基础设施
- 它在哪些情况下会失效

## 区分对象层次

常见混淆：

- 把协议机制和钱包实现混为一谈
- 把链能力和应用层封装混为一谈
- 把标准意图和实际落地情况混为一谈

因此分析时应显式指出对象层次。

## 比较时的原则

在 `scenario` 或 `evolution` 研究中：

- 先定比较维度
- 再收证据
- 最后比较

不要先凭印象下结论，再反向挑材料。

## 结论的正确粒度

好结论不是“更好”，而是：

- 在什么场景下更合适
- 为什么更合适
- 代价是什么
- 有哪些未决风险

## 允许保留不确定性

如果证据还不够，不要硬写确定判断。

允许写：

- 当前无法确认
- 现有证据仅支持到某一层
- 需要额外的 `L1/L2` 或实现验证
