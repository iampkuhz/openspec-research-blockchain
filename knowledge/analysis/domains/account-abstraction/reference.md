# 参考稿

## 研究对象

当前 `account-abstraction` 更适合作为一个长期维护的主题域，而不是一个单一对象。原因是它同时覆盖：

- 账户模型如何表达
- 谁来发起和打包交易
- 验证与执行在何处发生
- gas 由谁支付
- 用户授权是否可以从传统 EOA 路径中解耦

## 机制拆解

目前可以先把该 domain 分成四个问题簇：

1. 账户表达问题：账户是 `EOA`、`smart contract account`，还是两者之间的过渡模型。
2. 交易入口问题：请求是链原生交易，还是类似 `UserOperation` 的外部对象。
3. 验证与授权问题：谁验证签名、谁承担 replay / nonce / policy 约束。
4. gas 与执行问题：谁垫付 gas、谁聚合执行、谁承担失败成本。

## 设计原因

把 AA 作为 domain 管理，而不是直接等同于某个 EIP，有两个直接好处：

- 可以把“目标”与“实现路径”分开。
- 可以把“协议原生能力”与“钱包 / 基础设施封装能力”分开。

否则后续研究很容易出现两个错误：

- 先把所有 delegation、sponsorship、smart wallet 都混成一个问题。
- 先把生态工具链能力写成底层协议能力。

## 边界与前提

当前这个 domain case 不负责：

- 给出单一标准的完整结论
- 代表某条链或某个钱包产品背书
- 把所有“用户体验更好”的叙述自动视为 AA 价值

## 与相邻对象的关系

- 它依赖 `primitive` 来提供机制事实底座。
- 它依赖 `synthesis` 来组织多个 EIP 或方案之间的关系。
- 它会被 `decision` 复用到具体场景，如 `agentic-payment`。

## 价值与影响

如果这个 domain 维护得足够好，后续所有涉及授权、交易代付、自动化执行、smart account 的研究都会更容易复用，而不是每次重新解释“AA 到底指什么”。

## 当前可确认与待确认项

### 当前可确认

- `account-abstraction` 不是单一对象，必须拆成多个层次来管理。
- 术语层如果不先澄清，后续上层结论会失真。

### 待确认

- 哪些 EIP 应被视为该 domain 的核心底座对象。
- 哪些能力应被归类为协议原生，哪些只能算官方生态或第三方能力。
