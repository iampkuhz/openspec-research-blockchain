## 关键术语

| 术语 | 定义 | 在本题中的作用 |
|------|------|---------------|
| Evolution Layer | 标记对象解决哪一层问题的维度 | 避免错层比较的关键概念 |
| Replacement Claim | 声称某标准取代另一标准的判断 | 最需要证据约束的句型 |
| Protocol-Native AA | 依赖协议层变化实现 AA 的路径 | 区分协议层与应用层方案 |
| Application-Layer AA | 不修改协议层，通过合约实现 AA | EIP-4337 属于此类 |
| Compatibility Path | 为平滑落地采取的过渡方案 | 识别过渡 vs 变革 |
| Delegation | 将授权/执行权以受约束方式交给其他实体 | 常与 AA 混淆，需区分 |
| Native AA | 在共识层/协议层实现的账户抽象 | EIP-7560 的目标 |
| Counterfactual | 账户在链上部署前即可接收资产和交互 | CREATE2 带来的能力 |

## 演进框架

### 演进时间线

AA 领域 EIP 的历史演进可分为三个阶段：

**早期探索期（2017-2018）**：基础设施奠基
- EIP-712：结构化数据签名标准
- EIP-1014/CREATE2：确定性地址生成
- ERC-1271：合约签名验证标准

**第一次尝试期（2020-2021）**：三条路径竞争
- EIP-2938：协议层原生 AA 尝试（Withdrawn）
- EIP-3074：授权委托路径（Stagnant）
- EIP-4337：应用层 AA 方案（Final，胜出）

**协议演进期（2023-2024）**：协议层优化
- EIP-7560：原生 AA 再尝试（Draft）
- EIP-7702：EOA 代码化（Final）

演进关系：早期基础设施 → 第一次尝试（应用层胜出）→ 协议层优化（互补而非替代）

### 问题层分布

各 EIP 解决的问题层分布如下：

| 问题层 | 代表 EIP | 核心关注点 |
|--------|----------|-----------|
| Infrastructure | EIP-712 | 结构化数据签名格式 |
| Deployment | EIP-1014 | 确定性地址、counterfactual 部署 |
| Authorization | ERC-1271, EIP-3074 | 签名验证、授权委托 |
| Execution Entry | EIP-4337, EIP-7702 | 交易入口、执行抽象 |
| Protocol | EIP-2938, EIP-7560 | 协议层账户模型改造 |

## 各 EIP 定位

### 完整 EIP 列表

| EIP | 一句话定位 | 问题层 | 核心创新 | 当前状态 | 与 4337 关系 |
|-----|-----------|--------|----------|----------|-------------|
| EIP-712 | 结构化数据签名标准 | Infrastructure | 让合约能验证人类可读数据的签名 | Final | 基础依赖 |
| EIP-1014 | CREATE2 确定性地址生成 | Deployment | 允许在部署前预测合约地址 | Final | 支持 counterfactual 部署 |
| ERC-1271 | 合约签名验证标准 | Authorization | 让智能合约账户能被识别为可验证签名的实体 | Final | 基础依赖 |
| EIP-2938 | 第一次原生 AA 协议层尝试 | Protocol | 修改交易格式支持 AA | Withdrawn | 先驱/失败路径 |
| EIP-3074 | EOA 授权委托机制 | Authorization | AUTH/AUTHCALL 操作码 | Stagnant | 竞争路径 |
| EIP-4337 | 应用层账户抽象方案 | Execution Entry | Alt mempool + EntryPoint 合约 | Final | 基准方案 |
| EIP-7560 | 协议层原生账户抽象 | Protocol | 共识层 AA 支持 | Draft | 潜在演进 |
| EIP-7702 | EOA 代码存储能力 | Execution Entry | 为 EOA 添加代码存储 | Final | 互补增强 |

### 关键 EIP 详细定位

**EIP-712 (2017)**：基础设施奠基
- 核心贡献：定义结构化数据的签名格式
- 与 AA 的关系：为后续所有需要签名的 AA 方案提供基础设施
- 状态：Final，广泛采用

**EIP-1014/CREATE2 (2018)**：部署层突破
- 核心贡献：允许在合约部署前计算确定性地址
- 与 AA 的关系：使 counterfactual deployment 成为可能
- 状态：Final，EIP-4337 的 Factory 机制依赖此能力

**ERC-1271 (2018)**：授权层标准
- 核心贡献：定义合约如何验证签名（isValidSignature 接口）
- 与 AA 的关系：EIP-4337 的 Account Contract 通常实现此接口
- 状态：Final

**EIP-2938 (2020)**：第一次原生尝试
- 核心贡献：提出修改以太坊交易格式以支持原生 AA
- 失败原因：需要共识层改动，协调难度过高
- 遗产：证明了协议层改动的困难，促使社区转向应用层方案

**EIP-3074 (2021)**：授权委托路径
- 核心贡献：引入 AUTH/AUTHCALL 操作码
- 安全风险：合约获得 EOA 的完全控制权
- 当前状态：Stagnant，功能被 EIP-7702 部分覆盖

**EIP-4337 (2021)**：应用层突破
- 核心贡献：不修改协议层，通过 alt mempool + EntryPoint 合约实现 AA
- 成功因素：无需硬分叉，可快速迭代
- 状态：Final，当前 AA 生态的主流方案

**EIP-7702 (2024)**：EOA 代码化
- 核心贡献：为 EOA 添加代码存储能力
- 与 4337 的关系：官方规范定义的互补关系
- 状态：Final，Prague 升级内容

**EIP-7560 (2023)**：原生 AA 再尝试
- 核心贡献：在共识层实现原生账户抽象
- 与 4337 的关系：潜在演进方向
- 状态：Draft，实现证据不足

## 演进阶段分析

### 第一阶段：早期探索期 (2015-2018)

背景：以太坊上线初期，开发者开始意识到 EOA 模型的局限性。

关键进展：
- EIP-712：解决"签名人类可读数据"的基础设施问题
- EIP-1014/CREATE2：解决"部署前交互"的部署层问题
- ERC-1271：解决"合约如何验证签名"的授权层问题

阶段特征：
- 不直接挑战 EOA 模型，而是补充基础设施
- 为后续 AA 方案奠定技术基础
- 所有提案均成功落地（Final 状态）

### 第二阶段：第一次尝试期 (2020-2021)

背景：DeFi Summer 后，EOA 的 UX 限制成为明显瓶颈。

三条路径并行：

1. **协议层路径（EIP-2938）**：
   - 策略：直接修改协议层支持原生 AA
   - 结果：Withdrawn，协调成本过高
   - 教训：协议层改动需要极高的共识

2. **授权委托路径（EIP-3074）**：
   - 策略：通过新操作码让 EOA 授权合约
   - 结果：Stagnant，安全风险引发担忧
   - 问题：合约获得 EOA 完全控制权

3. **应用层路径（EIP-4337）**：
   - 策略：不修改协议，通过合约和链下服务实现
   - 结果：Final，生态全面落地
   - 成功因素：避免硬分叉，可快速迭代

阶段特征：
- 三条路径竞争，应用层路径胜出
- 证明了"先应用层验证，后协议层固化"的可行性
- 为后续演进提供了参照基准

### 第三阶段：协议演进期 (2023-2024)

背景：EIP-4337 生态成熟后，社区开始探索协议层优化。

两个方向：

1. **EOA 增强（EIP-7702）**：
   - 策略：为现有 EOA 添加代码能力
   - 与 4337 关系：互补，而非替代
   - 价值：让现有 EOA 用户也能享受部分 AA 能力

2. **原生 AA（EIP-7560）**：
   - 策略：在共识层实现真正的原生 AA
   - 与 4337 关系：潜在演进，但实现证据不足
   - 挑战：仍需协议层升级，协调难度高

阶段特征：
- 不再是非此即彼的竞争，而是分层互补
- 7702 作为过渡方案，7560 作为长期愿景
- 体现了"渐进式演进"而非"革命式替代"的策略

## 演进关系分析

### 核心观点：不是单线替代链

AA 领域的 EIP 不是简单的"旧→新"替代关系，因为它们解决的问题层不同：

```
Infrastructure (712) ──┐
                       ├──→ Authorization (1271, 3074) ──→ Execution (4337, 7702) ──→ Protocol (7560)
Deployment (1014) ─────┘
```

### 关键关系解析

**4337 vs 3074：竞争关系**
- 两者都试图解决"EOA 限制"问题
- 4337 选择"绕过 EOA"，3074 选择"增强 EOA"
- 3074 被标记为 Stagnant，4337 成为主流

**7702 vs 4337：互补关系**
- 官方规范定义两者为互补
- 7702 解决"EOA 代码化"，4337 解决"验证自定义化"
- 两者可以组合使用：7702 EOA + 4337 Paymaster

**7560 vs 4337：潜在演进关系**
- 官方文档提及 7560 是"长期方向"
- 但 7560 仍在 Draft 阶段，实现证据不足
- 7560 可视为 4337 的"协议层固化"版本

### 演进规律总结

1. **分层推进**：不同问题层独立演进，不是单线替代
2. **先应用后协议**：4337 的成功证明了"先验证后固化"路径
3. **互补而非替代**：7702 与 4337 展示了不同层方案的协同
4. **渐进式演进**：从 2938 的失败到 7560 的谨慎推进，体现了社区对协议层改动的审慎态度

## 技术趋势判断

### 短期趋势（1-2 年）

- **EIP-4337 生态将继续主导应用层 AA 方案**
  - 主要 Bundler 服务商持续投入
  - 钱包生态全面支持

- **EIP-7702 将与 4337 形成互补组合**
  - 官方规范定义的兼容性设计
  - Prague 升级后成为 EOA 用户进入 AA 生态的桥梁

- **EIP-3074 将保持 Stagnant 状态**
  - 功能被 7702 覆盖
  - 安全风险未解决

### 中期趋势（2-3 年）

- **EIP-7560 可能进入测试网阶段**
  - 官方团队持续投入研发
  - 仍需解决协议层协调问题

- **L2 链可能先于 L1 实现类 7560 功能**
  - L2 的升级协调成本低于 L1
  - 部分 L2 已有原生 AA

### 长期趋势（3-5 年）

- **协议层原生 AA 可能成为终极形态**
  - 核心开发者长期愿景
  - 【尚需验证】实现证据严重不足，时间线高度不确定

- **多路径共存将成为常态**
  - 不同场景选择不同方案
  - 4337 用于复杂验证逻辑
  - 7702 用于 EOA 增强
  - 7560（如实现）用于极致性能

### 关键不确定性

1. **EIP-7560 的实现时间表**：取决于协议层协调效率
2. **L2 的 AA 策略**：可能选择原生实现而非跟随 L1
3. **用户体验的权衡**：复杂 AA 功能 vs 简单 EOA 体验

## 可确认结论

以下结论基于官方规范文档及实现证据：

1. **AA 演进不是单线替代链**，不同 EIP 解决的问题层不同（infrastructure、authorization、execution、protocol）

2. **EIP-4337 是应用层 AA 的成熟方案**，不修改协议层，通过 EntryPoint 合约 + Bundler 服务实现

3. **EIP-7702 与 EIP-4337 是互补关系**，7702 解决 EOA 代码化，4337 解决验证自定义化

4. **EIP-3074 被标记为 Stagnant**，其功能被 EIP-7702 部分覆盖

5. **EIP-4337 生态已全面落地**，主流 Bundler、钱包、基础设施服务商均支持

6. **EIP-7560 仍在 Draft 阶段**，是协议层原生 AA 的尝试

7. **早期基础设施（EIP-712、EIP-1014、ERC-1271）均为 Final 状态**，为后续 AA 方案提供基础

8. **"先应用层验证，后协议层固化"成为社区共识**，4337 的成功证明了这一路径的可行性

## Evidence Gap

当前已知的证据缺口：

1. **EIP-3074 被标记为 Stagnant 的具体原因**：需要确认是技术问题、安全问题还是与 7702 的功能重叠

2. **EIP-7560 的实现进展**：作为 Draft 提案，是否有客户端实现或测试网部署？

3. **各 L2 对 EIP-7702 的适配时间表**：Prague 升级在主网激活后，L2 的跟进计划是什么？

4. **EIP-2938 的失败教训**：是否有官方 post-mortem 或社区复盘？

5. **EIP-4337 与 EIP-7560 的设计传承关系**：7560 是否明确吸收了 4337 的经验？

6. **EIP-7702 的实际采用数据**：Prague 升级后，有多少 EOA 转换为 7702 账户？
