## 关键术语

| 术语 | 定义 | 在本题中的作用 |
|------|------|---------------|
| SET_CODE_TRANSACTION | EIP-7702 引入的新交易类型（类型 0x04），用于设置 EOA 的代码 | 7702 的核心机制入口 |
| Authorization Tuple | 授权元组，包含 chain_id、address、nonce、y_parity、r、s | EOA 授权特定代码的签名数据 |
| Delegation Designator | 委托指示符，0xef0100 + 地址，存储在 EOA 代码中指向委托合约 | 实现代码委托的关键机制 |
| Code Storage | EOA 的代码存储能力，由 7702 新增 | 使 EOA 可以像合约一样执行代码 |
| Authority | 授权地址，即签署 authorization tuple 的 EOA | 7702 交易的授权主体 |
| Delegated Code | 被委托的合约代码，实际执行逻辑 | 由用户选择，third-party |

## 组件架构

### 组件分层说明

EIP-7702 引入了协议层的新能力，其组件位于不同层级：

**能力归属分类定义**：

- **protocol-native**：EIP-7702 规范本身定义的协议层能力，由以太坊协议强制执行
- **third-party**：完全由独立第三方提供的代码或服务，需额外信任假设

**组件分层说明**：

| 层级 | 组件 | 说明 |
|------|------|------|
| L1 协议层 | SET_CODE_TRANSACTION | 新交易类型，协议原生支持 |
| L1 协议层 | Authorization 验证 | 协议层验证授权签名 |
| L1 协议层 | Code Storage | EOA 代码存储，协议层能力 |
| L2 应用层 | Delegated Code | 用户选择的委托合约代码，third-party |
| L2 应用层 | Authority (EOA) | 授权主体，用户控制的 EOA |

**架构说明**：

- **L1 协议层**：7702 的核心创新在协议层，为 EOA 添加了代码存储能力
- **L2 应用层**：实际执行逻辑由用户选择的委托合约决定
- **关键设计**：协议层只负责"允许 EOA 有代码"，不负责"代码做什么"

### 组件关系

```
Authority (EOA)
    ↓ 签署
SET_CODE_TRANSACTION
    ↓ 包含
Authorization Tuple
    ↓ 验证通过后
Code Storage (EOA State)
    ↓ 存储
delegation designator (0xef0100 + address)
    ↓ 指向
Delegated Code (委托合约)
```

## 核心流程

### 7702 交易执行流程

**流程步骤**：

1. **交易构造**：用户通过钱包创建 7702 交易，包含 authorization tuple，指定要委托的合约地址
2. **双重验证**：协议层验证交易签名和 authorization tuple 签名，确保授权有效性
3. **代码设置**：验证通过后，EOA 状态中添加 delegation designator（0xef0100 + 委托地址）
4. **委托执行**：后续对 EOA 的调用将委托到指定合约执行

### Authorization Tuple 结构

| 字段 | 类型 | 说明 |
|------|------|------|
| chain_id | uint256 | 防止跨链重放 |
| address | address | 委托合约地址 |
| nonce | uint64 | EOA 的 nonce，防止重放 |
| y_parity | uint8 | 签名恢复 ID |
| r | uint256 | 签名 r 值 |
| s | uint256 | 签名 s 值 |

## 设计取舍

### 为什么 7702 能解决 3074 的安全问题

**EIP-3074 的安全问题**：
- AUTH 操作码让合约获得 EOA 的完全控制权
- 恶意合约可以代表 EOA 执行任意操作
- 用户一旦授权，无法限制合约的行为范围

**EIP-7702 的解决方案**：

| 方面 | EIP-3074 | EIP-7702 |
|------|----------|----------|
| 授权对象 | 任意合约获得完全控制权 | 代码委托，控制权在代码逻辑 |
| 可撤销性 | 困难，需依赖合约实现 | 通过新交易可更换委托代码 |
| 可见性 | 授权状态不透明 | delegation designator 存储在链上 |
| 限制能力 | 无法限制授权范围 | 代码逻辑可自定义限制 |

**核心差异**：
- 3074："授权合约代表我行动"（开放式授权）
- 7702："我的地址执行这段代码"（代码委托）

### 为什么是新的交易类型

**设计取舍对比**：

| 方案 | 优点 | 缺点 | 7702 的选择 |
|------|------|------|-------------|
| 复用现有交易类型 | 无需新交易类型 | 难以区分 7702 交易，协议复杂度增加 | 不采用 |
| 新交易类型 SET_CODE_TRANSACTION | 清晰区分，协议层原生支持 | 需要客户端升级 | 采用 |

**选择原因**：
- 协议层原生支持，确保所有客户端一致处理
- 清晰语义：这是"设置代码"的特殊交易
- 与现有交易类型不混淆，避免意外行为

### 与 4337 的设计哲学差异

| 维度 | EIP-4337 | EIP-7702 |
|------|----------|----------|
| 层级 | 应用层 | 协议层 |
| 修改范围 | 不修改协议，合约实现 | 修改协议，新交易类型 |
| 地址变化 | 用户迁移到新地址（合约账户） | 地址不变（原 EOA） |
| 角色复杂度 | Bundler、EntryPoint、Paymaster 等多角色 | 无额外角色 |
| 灵活性 | 高（自定义验证逻辑） | 中（依赖委托代码） |
| 部署成本 | 需要部署合约账户 | 无需部署 |

**设计哲学**：
- 4337："绕过 EOA，创建新的账户模型"
- 7702："增强 EOA，让现有地址获得合约能力"

## 能力边界

### 7702 vs 4337 能力对比

| 能力 | EIP-7702 | EIP-4337 | 说明 |
|------|----------|----------|------|
| EOA 地址保持不变 | ✅ | ❌ | 7702 的核心优势 |
| 无需部署合约 | ✅ | ❌ | 7702 降低门槛 |
| 协议层原生支持 | ✅ | ❌ | 7702 是协议层能力 |
| 自定义验证逻辑 | ⚠️ | ✅ | 7702 依赖委托代码 |
| 多签/社交恢复 | ⚠️ | ✅ | 4337 更灵活 |
| Paymaster 代付 gas | ❌ | ✅ | 7702 无此能力 |
| 批量操作 | ⚠️ | ✅ | 7702 依赖委托代码实现 |
| 跨链兼容性 | ✅ | ⚠️ | 7702 是协议层，4337 依赖链下基础设施 |

**说明**：
- ✅ 原生支持
- ⚠️ 依赖实现
- ❌ 不支持

### 7702 能解决什么

**协议层能力**：
1. 让 EOA 地址可以执行合约代码
2. 无需部署新合约账户
3. 保持地址不变，资产不迁移
4. 协议层原生支持，无需链下基础设施

**应用场景**：
1. EOA 用户享受部分 AA 能力（如批量操作）
2. 与 4337 Paymaster 结合，实现 gas 抽象
3. 为现有 DApp 提供更灵活的交互方式

### 7702 不能解决什么

**能力限制**：
1. **自定义验证逻辑受限**：依赖委托代码的能力，不如 4337 灵活
2. **无原生 Paymaster 支持**：无法像 4337 那样原生支持代付 gas
3. **无 alt mempool**：仍需传统交易传播机制
4. **代码安全风险**：委托代码的漏洞会影响 EOA 安全

**与 4337 的互补点**：
- 7702 提供"地址不变 + 协议层支持"
- 4337 提供"灵活验证 + Paymaster"
- 两者组合：7702 EOA + 4337 Paymaster = 地址不变的 gas 抽象

### 角色归属分类

**分类定义**：

- **protocol-native**：EIP-7702 规范本身定义的协议层能力，由以太坊协议强制执行
- **third-party**：完全由独立第三方提供的代码或服务，需额外信任假设

**角色归属表**：

| 角色 | 作用说明 | protocol-native | third-party | 状态 |
|------|----------|-----------------|-------------|------|
| SET_CODE_TRANSACTION | 新交易类型，设置 EOA 代码 | ✅ | - | live |
| Authorization 验证 | 协议层验证授权签名 | ✅ | - | live |
| Code Storage | EOA 代码存储能力 | ✅ | - | live |
| Delegated Code | 用户选择的委托合约代码 | - | ✅ | live |
| Authority (EOA) | 授权主体，用户控制的地址 | ✅ | - | live |

**说明**：EIP-7702 是协议层能力，核心机制（交易类型、验证、存储）都是 protocol-native。只有委托的代码逻辑是 third-party，由用户自行选择。

## 相关协议关系

### 与 EIP-3074 的关系

- **功能重叠**：两者都试图增强 EOA 能力
- **安全模型不同**：
  - 3074：开放式授权，合约获得完全控制权
  - 7702：代码委托，控制权在代码逻辑
- **官方立场**：3074 被标记为 Stagnant，7702 成为推荐方案
- **关系**：7702 替代了 3074 的部分场景，但解决了其安全问题

### 与 EIP-4337 的关系

- **互补关系**：官方文档明确说明兼容性设计
- **能力互补**：
  - 7702：地址不变、协议层支持
  - 4337：灵活验证、Paymaster
- **协同场景**：7702 EOA + 4337 Paymaster
- **关系**：相邻层协作，而非竞争替代

### 与 EIP-7560 的关系

- **不同路径**：
  - 7702：增强现有 EOA
  - 7560：全新的原生 AA 账户模型
- **潜在演进**：7560 可能吸收 7702 的部分设计
- **关系**：并行探索，长期可能收敛

## 可确认结论

以下结论基于官方规范文档：

1. **EIP-7702 是协议层能力**，通过新交易类型 SET_CODE_TRANSACTION 实现

2. **核心机制是代码委托**，EOA 存储 delegation designator 指向委托合约

3. **解决了 EIP-3074 的安全问题**，通过代码委托替代开放式授权

4. **与 EIP-4337 是互补关系**，官方规范定义兼容性设计

5. **EOA 地址保持不变**，无需资产迁移

6. **无需部署合约账户**，降低用户门槛

7. **能力受限**，无原生 Paymaster 支持，自定义验证逻辑依赖委托代码

8. **是 Prague 升级的重要内容**，需要客户端升级支持

## Evidence Gap

当前已知的证据缺口：

1. **Prague 升级后主网激活的具体时间**：需要确认实际区块高度

2. **钱包支持情况**：哪些钱包已支持 7702 交易构造和签名

3. **与 4337 集成的实际案例**：理论互补性已有，实际集成案例待验证

4. **委托代码的安全审计情况**：用户选择委托代码的安全风险

5. **7702 的实际采用数据**：Prague 升级后，有多少 EOA 转换为 7702 账户
