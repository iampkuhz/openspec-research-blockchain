# 参考稿

## 研究对象

`EIP-4337` 需要回答的不是“它好不好”，而是“它到底把账户抽象的哪一部分放到了哪一层”。

## 机制拆解

从当前已知框架看，4337 至少包含以下最小路径：

1. 用户形成一个 `UserOperation`。
2. `UserOperation` 被发送到 `bundler`，而不是直接作为链原生 transaction 广播。
3. `bundler` 对候选操作做筛选、模拟或打包。
4. 打包后的调用通过 `EntryPoint` 进入验证与执行流程。
5. `paymaster` 之类的角色可以介入支付策略，但其能力边界仍需以规范和实现证据细化。

这套结构的直观含义是：4337 试图在不要求底层协议立即重构账户模型的前提下，把部分账户可编程性和 gas 支付灵活性搬到协议之上的一层。

## 设计原因

一个初步判断是，4337 的核心设计张力在于：

- 希望获得更可编程的账户能力
- 但不希望把全部改动压到共识层升级

因此它引入了新的请求对象、专门角色和统一入口，而不是直接修改传统 transaction 路径。这种路线的潜在优点，是更容易在现有生态中逐步落地；代价则可能是：

- 引入新的中间角色与基础设施假设
- 需要额外讨论打包、模拟、失败处理和策略执行的边界

## 边界与前提

当前需要特别避免的误写：

- 把某个钱包已经支持的 sponsor 模式直接写成 4337 协议原生能力。
- 把第三方 bundler 服务提供的能力直接写成所有链或所有实现默认具备的能力。

因此本研究必须明确区分：

- 4337 规范本身定义了什么
- 官方实现或参考实现提供了什么
- 第三方基础设施额外封装了什么

## 与相邻对象的关系

4337 很可能是 AA 主题里的底层核心对象之一，但它不必然覆盖所有 delegation、authorization 或协议原生账户模型问题。后续仍需和其他 EIP 或路线做分层比较。

## 价值与影响

如果 4337 的边界能被讲清楚，上层研究至少能更准确回答三件事：

- 哪些“AA 能力”其实只是 4337 生态能力
- 哪些上层场景依赖 4337 的哪一层
- 哪些时候不应把 4337 当成所有 AA 路线的总括

## 当前可确认与待确认项

### 当前可确认

- 4337 不是简单的“多一个钱包功能”，而是一套包含新对象与新角色的执行路径设计。
- `UserOperation` 与链原生 transaction 的区分，是理解 4337 的入口之一。

### 待确认

- `EntryPoint` 在不同材料中的职责表述是否完全一致。
- `paymaster` 的边界在规范、参考实现和商业服务中是否存在明显偏差。
